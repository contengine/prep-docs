1. Introduction and Overview

This document explains the specifications of the Auto Tag API in PREP.

Auto-tagging a PDF document is a three-step process:

  • Request an upload URL (Initiate upload for Auto Tag)
  • Upload the file for auto-tagging
  • Poll for processing status

The Auto-tag API exposes three RESTful endpoints:

  • POST v3/process/init-auto-tag/ — Starts the auto-tagging workflow for a PDF file. This call kicks off the auto-tagging process and returns a unique, signed URL that the file will be uploaded to in the next step.
  • PUT https://static-storage-v3-continualengine.com/…/signed_url/ — Uploads the file to Static Storage. PUT the file directly to the signed URL returned above.
  • POST process/ping/ — Checks the status of the auto-tagging job and returns the download link once ready.

2. API ID/KEY setup

The API key will be sent in email.

Every request to a PREP API endpoint must include your api-id and app-key headers — requests without them are rejected.

The tenant header is required for all APIs:

--header 'tenant: portal.prep'

Your tenant value will also be shared with you over email.

3. API Specs

Base URL: https://ingprfl.continualengine.com

Every endpoint below is relative to this Base URL — e.g. /v3/process/init-auto-tag/ is called as https://ingprfl.continualengine.com/v3/process/init-auto-tag/.

3.2 Upload file

3.2.1 Upload file to process

PUT the file directly to the signed Static Storage URL returned in step 3.1.

Endpoint: PUT <upload_url> — the full signed URL returned in the 3.1 Auto tag API response, not a fixed path off the Base URL.

This request goes straight to static-storage-v3-continualengine.com, not to the PREP API host — do not add your api-id/app-key headers here.

Response

This is a direct pre-signed upload to S3, not a PREP API call — on success it returns an empty body with an ETag header, not JSON.

ResultMeaningStatus code
SuccessEmpty body. The file was received — proceed to poll 3.3 Auto tag file status API using the upload_id from step 3.1.200
Expired URLThe signed URL's X-Amz-Expires window has passed. Request a new upload URL via 3.1 Auto tag API.403
Signature mismatchThe URL was modified, or the file content-type doesn't match what was signed for.403

3.4.2 Upload files to process (batch)

PUT each file directly to its own signed Static Storage URL returned above — the same mechanism as 3.2 Upload file, repeated once per file in the batch.

Endpoint: PUT <upload_url> — a different signed URL per file, taken from that file's own upload_url in the batch response above.

Every file in the batch has its own upload_url and must be uploaded individually. Uploading only one file does not upload the rest of the batch.

Response

Same as 3.2 Upload file: each successful upload returns an empty body with an ETag header (200), not JSON. Once every file in the batch has been uploaded, poll 3.5 Auto tag batch status API with the shared batch_id to track processing.

3.4.2 Upload files to process (batch)

Request

# repeat once per file, using that file's own upload_url
curl --location --request PUT '<upload_url for sample1.pdf>' \
--header 'tenant: portal.prep' \
--header 'Content-Type: application/pdf' \
--data-binary 'path-to-file/sample1.pdf'

# then again for sample2.pdf, sample3.pdf, ... using each one's own upload_url

3.5 Auto tag batch status API

3.5.1 Batch processing status

POST the batchId from the batch upload response to check the status of every file in that batch.

Endpoint: POST /v3/batch/ping/

Payload of batch status

KeyValue type
batchIdString — the batch_id returned from the batch upload call

Response of batch status

The batch status API returns an array of objects, one per file. If a file's status is completed, its object includes a file key with the download URL:

{
  "status": "completed",
  "upload_id": "51debdae-88a8-4138-a954-42c7f1dd7ff2",
  "file": "https://static-storage-v3-continualengine.com/media/tagged/sample1.pdf?sign=20dppoi2nd29y4-d2bom11lo9aslciem",
  "batch_id": "96430b40-92d3-4d60-90dd-535a49fbce8d"
}

If the file is still in-progress, it won't have a file key — instead it has a value key showing the percentage processed so far:

{
  "status": "in-progress",
  "upload_id": "73179df7-c0a2-492a-8dbc-a925c07d9a24",
  "value": "4%",
  "batch_id": "96430b40-92d3-4d60-90dd-535a49fbce8d"
}

Each file's upload_id is unique and can also be used to check that single file's status individually, as described in 3.3 Auto tag file status API.

KeyDescription
statusCurrent processing state of this file within the batch: completed or in-progress.
upload_idIdentifies which file in the batch this entry refers to — matches the upload_id returned for that file in 3.4 Auto tag batch API.
fileOnly present when status is completed. Signed download link for this file's tagged output. Expires within 15 minutes.
valueOnly present when status is in-progress. Percentage of this file processed so far (e.g. "4%").
batch_idIdentifier shared by every file in the same batch — the same value you posted to this endpoint.

4. Error Codes

PREP can respond with errors with the below codes.

KeyDescription
statusAlways "failed" on an error response.
errorHuman-readable description of what went wrong — safe to show directly to an end user or log for debugging.
ErrorCauseStatus code
Bad RequestClient sent bad input — a missing field or a value of the wrong type.400
UnauthorizedNot authenticated — missing, invalid, or expired api-id / app-key credentials.401
ForbiddenAuthenticated but not allowed to perform this action.403
Not FoundThe resource being requested (e.g. an upload_id or batch_id) doesn't exist.404
Too Many RequestsClient exceeded the rate limit or quota for their account (see 6. Rate Limits).429
Expectation FailedThe uploaded file could not be processed — e.g. the file is corrupt or unreadable.417
Internal Server ErrorSomething genuinely broke on PREP's side, with no clearer category — meant for unexpected server bugs.500
4. Error Codes

Response

// Bad Request — 400
{ "status": "failed", "error": "Invalid argument" }

// Unauthorized — 401
{ "status": "failed", "error": "Not authenticated" }

// Forbidden — 403
{ "status": "failed", "error": "Forbidden" }

// Not Found — 404
{ "status": "failed", "error": "Resource not found" }

// Too Many Requests — 429
{ "status": "failed", "error": "Either out of resource quota or reaching rate limiting" }

// Expectation Failed — 417
{ "status": "failed", "error": "The file is corrupt." }

// Internal Server Error — 500
{ "status": "failed", "error": "Internal error." }

  • No. of documents that can be uploaded by a user — 15

7. Libraries (Dependencies)

8. Versioning & updates

We use Semantic Versioning (SemVer) for our API. Versions are numbered as major.minor.patch. Breaking changes will increment the major version, while new features and improvements will be reflected in the minor version. Bug fixes will trigger a change in the patch version.
